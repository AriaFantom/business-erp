# Repository Guidelines

## Project Structure & Module Organization

AdonisJS 7 serves an Inertia/React frontend. Backend `app/` contains controllers, services, VineJS validators, and Lucid models. Routes/middleware live in `start/`, configuration in `config/`, providers in `providers/`, and migrations/seeders in `database/`. Frontend code is under `inertia/`; Edge templates are in `resources/views/`.

## Backend Architecture & Request Flow

Define routes in `start/routes.ts`; authenticated routes use session auth, Bouncer, and—where applicable—`ensure_module_middleware.ts`. Controllers authorize, validate, call a service, then render or redirect.

Put business rules and state transitions in `app/services/`. Multi-record writes use Lucid transactions and row locks where needed. Record mutations through `audit(...)` in the same transaction. Use `DomainError` for database-dependent failures; Vine handles request-shape errors.

Invitation and login email matching trims and lowercases addresses without removing dots or tags. Existing provider-normalized accounts remain accessible through a password-verified legacy lookup when no exact account matches; never rewrite or merge those accounts. Invitation acceptance locks and consumes the invitation inside the user-creation transaction; delivery state is separate from pending/accepted status. Keep all pending invitations visible, including expired links, so they can be retried; refresh the list on focus and at 15-second intervals while visible.
Invitation emails use the current dashboard branding name and embed the private branding icon as an inline attachment; email delivery must still succeed with the name-only fallback when no icon exists or the icon cannot be read.

Roles have a persisted, highest-first `rankPosition`. The old `parentRoleId` remains only for compatibility; authorization and the management UI use rank order. The Owner rank stays fixed first. Managers with `roles.update` can drag only ranks below their own highest assigned role, with all of their own roles fixed. Feature permissions are still the union of assigned roles. Serialize role creation, deletion, reorder, and assignment with the shared database lock, recheck authorization after acquiring it, and audit writes in the same transaction. Preserve custom rank positions when seeding. User role editing exposes server-calculated editability and allowed roles; never allow self-editing, Owner editing, or an empty role set.
Workspace owners implicitly hold every active permission on both the server and client; authorization must not depend on a possibly stale persisted Owner-role permission list. When adding permissions intended for existing system roles, update the additive production-upgrade seeder and include a forward migration for Railway deployments that run migrations without seeders.

User revocation is reversible (`users.isActive`); preserve accounts and records. Deny revoked users at login and terminate their existing sessions on the next request. Revoke/restore is target-aware (`users.remove`), excluding self and Owner and respecting ranked-role boundaries; serialize and audit access changes.

Application identity lives in `app_settings` under `dashboard_branding`, and the display currency lives under `app_currency` with INR as the fallback. Only the owner may change the business name, private icon, or ISO currency from the single Settings form. Save these settings and their audit record transactionally, clean replaced icons after commit, and invalidate cached invoice/quotation PDFs when currency changes. Currency changes relabel existing numeric amounts without exchange-rate conversion. Share branding and currency through Inertia; branding drives the sidebar, browser-title suffix, authenticated favicon, and invitation email.
The unset branding name defaults to BusinessERP across server and client surfaces. Invitation messages use the saved business name as sender display name, subject, and body, plus the inline private icon, falling back to the name alone when the icon is unavailable; generated invoice and quotation documents use the same saved business name and their cached copies are invalidated when the name changes.

System navigation is ordered Settings, Role Management, Users & Invitations, then Modules. Users and Invitations share one tabbed page, but load and expose each tab's data independently according to `users.view` and `users.invite`; invitation polling runs only when that data is available. Keep the legacy branding and invitation URLs as redirects while preserving existing mutation endpoints.
The Users tab displays active accounts by default and keeps revoked accounts in a separate restorable view; revocation never deletes an account.

Models extend generated `database/schema.ts`; never edit it or `.adonisjs/` manually. Configurable module definitions belong in `app/services/modules/registry.ts`; reports are always available and remain protected by `reports.view`, not the module gate. S3/MinIO files stay private and stream through authorized app routes. Web-only schedules are registered by `providers/scheduler_provider.ts`.
New routes must also pass a clean production build where `.adonisjs/` is regenerated from the committed source. Avoid making controller compilation depend on locally stale generated route-name types; use explicit redirect paths when the route is introduced in the same change.

## Build, Test, and Development Commands

- `npm install` installs dependencies (Node 24+); `npm run dev` starts HMR.
- On Windows, `.\dev.ps1 setup` prepares a first-time development environment;
  `.\dev.ps1` starts the Docker infrastructure and host-run npm app thereafter.
- `docker compose -f docker-compose.dev.yml up -d` starts local infrastructure
  when using the manual workflow.
- `node ace migration:run && node ace db:seed` prepares the database.
- `npm run build` creates production output; `npm start` runs it.
- `npm test` runs Japa; target suites/files with `node ace test --suites=unit` or `--files="tests/unit/pricing.spec.ts"`.
- `npm run lint`, `npm run typecheck`, and `npm run format` check quality.

Vite pre-bundles `motion/react` for the lazy-loaded Modules and Production Floor pages. Browser tests use a separate Vite cache so they cannot invalidate assets served by an active development session.
The test runner forces a distinct `*_test` PostgreSQL database (default `dev_test`, override with `TEST_DB_DATABASE`) before application boot. Create and migrate that database before running Japa; never point tests at `dev`, since existing test helpers truncate tables. Test HTTP sessions use the in-memory store so Japa's session and CSRF clients share fixture state; development and production keep their configured store.

## Coding & Testing Conventions

Use TypeScript, two-space indentation, single quotes, Prettier, and the AdonisJS ESLint preset. Use `PascalCase` for classes/components, `camelCase` for symbols, backend `snake_case.ts`, and frontend kebab-case files. Prefer `#services/*` and `@/*` aliases. Name Japa tests `*.spec.ts`; use unit tests for pure logic and functional tests for routes, authorization, persistence, and regressions.

For Inertia mutations that replace server-backed navigation or application configuration, disable preserved component state on success and invalidate prefetched pages so the persistent layout and edited page consume the same response snapshot.

The products list offers both a primary, mobile-friendly three-step Basics, Details, Review dialog in `inertia/components/catalog/new-product-dialog.tsx` and a one-page quick add dialog. Keep the guided form's client-side step checks aligned with `createProductValidator`, and keep its fields mounted across steps so `SkuField` remembers manually edited SKUs. Quick add collects name, SKU, category, and an optional product picture; it omits description and percentages. Both forms submit through `products.store`, which inherits omitted profit and tax percentages from the selected category and saves an optional image using catalog image storage. Cover default inheritance, explicit overrides, and image creation in `tests/functional/products.spec.ts`.
Products and components expose name-only edit dialogs; their SKU is immutable after creation and never sent by the edit form. Material and component creation dialogs use equal-width, responsive fields and full-width selectors.
Materials also expose name-only editing. Materials, components, products, and machines may be permanently deleted only when they have no stock or business history; expose the server-provided blocker and keep Archive/Retire as the alternative. Deletion must lock and recheck in a transaction, audit the mutation, and rely on restrictive database foreign keys plus typed catalog-reference columns for polymorphic history. Clean owned private files only after commit.

Product profit analysis keeps saved defaults, ordinary backend-calculated prices, and minimum profit targets distinct. Minimum targets prefer the category profit percentage (including an explicit zero), then product and global fallbacks, and round upward to the next cent so the target is never understated. Default-price forms warn below target without blocking; prices are displayed before tax. Use the shared currency formatter for dashboard money and pass the current currency into invoice and quotation PDFs; do not hardcode currency symbols.
On the product detail page, place lifecycle and Custom badges directly beside the product name and keep the name-edit action as a right-aligned pencil icon in the header.
Keep the product Images and QR cards aligned as a two-column desktop row, with the 3D model files card spanning the full row beneath them so its filter and table columns have enough width.

New purchases use fixed purchase-level shipping and invoice-tax amounts. Allocate both charges proportionally by pre-charge goods value with deterministic, cent-exact remainders; store the allocations and four-decimal landed unit cost on each line. Confirmation uses landed cost for inbound stock and weighted-average valuation, while supplier returns always credit only the original goods unit cost. Omitted invoice tax retains the legacy per-line-tax path for existing callers, but never combine both tax modes. Cover allocation, confirmation, payment, validation, legacy compatibility, and return-credit behavior in `tests/functional/purchases.spec.ts`.
Purchases may also contain machine lines with a name, optional model, whole quantity, and unit price. Confirmation creates one machine per unit exactly once and records that machine's landed unit cost, including its proportional shipping and invoice tax; machine supplier returns are unsupported. Manually created machines retain a null acquisition cost and display it as Not recorded.

Production consumption accepts an optional entered unit and converts compatible mass (`mg/g/kg`), volume (`ml/l`), and length (`mm/cm/m`) families to each catalog item's stored unit before merging, stock validation, costing, audit, returns, and recipe learning. Pieces and unsupported custom units remain exact-only. Persist production quantities at nine-decimal precision and reject incompatible, over-precise, zero-after-conversion, or overflowing values instead of rounding them away. Job stages keep `durationMinutes` on the wire, but the interface edits separate whole hours and `0–59` minutes. Force done is the same production flow: drafts must supply the normal setup and active jobs reuse saved setup, all writes commit in one locked transaction, and machine/labour cost uses the sum of every configured stage while normal completion remains elapsed-time based.
Quotation estimator and custom-BOM quantities use the same compatible unit families and server-side conversion. Keep entered units editable in the interface, preserve physical quantity when switching units, and normalize saved quotation BOM quantities and costing to each catalog item's stored unit. Pieces and custom units remain exact-only.
Unit selectors must return no options while no inventory item is selected; never render a shadcn `SelectItem` with an empty-string value because it crashes the page during render.
The owner-managed Units settings store exact positive factors relative to a fixed reference unit per category. Do not infer relationships for legacy custom codes. Conversion callers must use the registry under the shared transaction lock and mark participating units used before commit; management takes the exclusive lock and cannot revise locked factors.
Catalog units remain the stock basis; finished products and machines must resolve to whole pieces. Purchase, quotation, order, and invoice unit snapshots keep the entered quantity, unit, factor, and price separate from normalized stock quantities. Returns accept the stored unit or the original entered unit and use the original snapshot, even when the unit is archived. Recipes and quotation estimates remain per individual product.
Completed jobs create machine-attributed production outputs from rollout onward. Confirmed orders and POS allocate sold units oldest-output-first; returns restore the exact allocation. Machine sales profit uses tax-exclusive sale value minus the source job's captured unit cost. Keep acquisition cost and standalone machine expenses separate, and do not subtract job expenses twice. Invoice voiding removes tracked revenue without creating a stock return. Existing and otherwise unattributed stock remains unassigned rather than being guessed.

Use the shared shadcn `Select` in dashboard dialogs instead of native HTML selects so option menus inherit the application theme, accessibility behavior, and overlay positioning. Keep `SelectItem` entries inside `SelectGroup`.

Dashboard data tables use the shared `Table` quick filter so loaded rows remain searchable even on detail and reporting pages. Keep row-level actions compact and icon-only, with descriptive accessible labels and titles; primary page and dialog actions retain text labels. Supplier details are editable together from the suppliers list. Catalog primary-image controls for products, components, and materials accept a local file, a pasted clipboard image, or a direct image URL; linked images are downloaded in the browser and therefore require the source to allow cross-origin downloads.
Material and component image columns are always visible and their original clickable image tiles open the file, clipboard-paste, and link dialog. Show permanent deletion only when the server reports no deletion blocker; never render a disabled delete control or blocker-warning text, and let linked records show Archive or Restore instead. Keep product QR and attachment management on the product detail page rather than duplicating them in the products table.
Customer detail editing updates the name, contact, tax, address, and credit-limit fields together without changing account status or financial history; lock the customer and audit the edit in the same transaction. Material and component Quick add reuse the newest active item settings for that catalog kind across all filters, but never copy identity, images, inventory, or history, and ignore an inactive default supplier.

Quotation cost estimates are internal per-product snapshots made from selected material/component default costs plus an extra-cost amount and markup on cost. Preview and save must share the server calculator; estimate-derived prices require a matching catalog-cost fingerprint and round upward to the next cent. Estimates may apply to existing or custom quotation lines but never reserve stock, create production activity, update product pricing, or replace an existing product recipe. Customer PDFs expose only the chosen selling price and tax, while internal quotation details may show the saved estimate breakdown.

The module settings page uses the full dashboard content width, with Save and conditional Reset actions right-aligned in the page-title header. Presets and the connected workflow share one configuration card whose header introduces the presets without duplicating that text in the content, with the four large equal module-style preset options constrained and centered above the workflow. Operational stages use constrained columns with visible gaps and frequent, closely staggered MagicUI-style `AnimatedBeam` connections. Reports are not configurable and must not appear in this workflow or its presets.

## Production Deployment & Data Safety

Run `./deploy.sh update` for releases; it always fast-forwards `main`, then migrates, seeds, and health-checks without backing up by default. `migrate-only` also skips seeders; `WITH_BACKUP=true` opts a release into a verified backup. Use reviewed expand/contract migrations. Never run `docker compose down -v`, `./deploy.sh nuke`, or destructive rollbacks; copy backups off-host.

When `INFLUX_ENABLED=true`, HTTP startup requires a reachable InfluxDB 2.x `/ready` endpoint and a token-accessible configured organization/bucket; incomplete configuration or an unavailable store must fail startup. Keep the boot probe independent of container-resolved services such as the application logger because it runs before the container is ready. Railway's `InfluxDB` service uses a persistent `/var/lib/influxdb2` volume and the app connects over its private domain on port 8086; keep its initialization token in Railway variables, never in the repository. Local development may leave Influx disabled.

## Commits, Pull Requests & Guide Maintenance

Use concise imperative commits, optionally prefixed with `feat:` or `fix:`. PRs describe behavior, database/configuration impact, verification, linked issues, and UI screenshots when relevant. Never commit secrets or generated output.

For every repository change, re-read and update `AGENTS.md` in the same patch so its architecture, commands, paths, and conventions remain accurate. Fold durable guidance into the relevant section; do not append a change log.
